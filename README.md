# OfferFolio · 求职橱窗

> 由 **EckyStudio** 发起与维护。

**把简历发出去，不再石沉大海。**

> 带后台的开发者求职作品集 —— 网页里改内容，本地或通过单个 Docker 镜像运行；项目与成就条目可添加链接或图片作为证据，并查看所有公开访问及专属投递来源。
>
> *A portfolio that tells you who looked, what they read, and for how long.*

系统用于求职投递阶段：把展示页链接附在简历或投递信息中，供招聘方查看个人经历、项目和能力证据。页面不配置求职状态或个人岗位意向，投递材料已经提供本次岗位的上下文。

OfferFolio 默认按**求职期间的短期展示页**设计，不要求长期公开托管。没有服务器时，也可在后台导出不依赖 OfferFolio 服务端的静态页面，免费托管到 GitHub Pages 等静态站点服务。静态副本不会记录访客、模块停留或投递来源；公开的内容和图片、视频会随导出包交给静态托管平台，发布前请确认适合公开。后台默认开启搜索引擎限制：`/robots.txt` 建议爬虫不要抓取站点，公开页同时输出 `noindex`、`nofollow`、`noarchive` 等 robots 元数据，尽量减少搜索收录、快照和不必要的爬虫访问；需要主动公开时，可在“布局调整”中关闭这一项。它属于隐私保护和降低长期托管暴露面的默认措施，不是访问控制，也不能保证所有爬虫遵守，或自动清除已经收录的 URL 和第三方副本。结束求职展示时，应删除静态托管上的发布文件或停止公开服务；若页面已经被搜索引擎收录，还需使用相应站长工具申请移除。

OfferFolio = **Offer** + **Folio**（portfolio 的词根，本义"一叠可携带的纸页"）。名字就是目的：作品集不是终点，拿到 offer 才是。

---

## 为什么做它

投递季最稀缺的不是机会，是**信息**。

你把 PDF 发给五家公司，然后就什么都不知道了：HR 到底点开了没有？他是认真看了你的项目列表，还是划到最后一页找邮箱？哪一家第二天又回访了一次？

传统作品集模板解决的是"展示"。OfferFolio 补上的是另一半——**展示 + 反馈闭环**：

运行带后台的服务端版本时，公开主页访问会进入后台记录；给每次投递附上专属链接后，还能区分具体投递来源。记录包括访问时间、来源页、UTM 参数、入口模块、终端信息、模块导航点击和可见停留时长，也会统计联系、简历下载、GitHub 与 Gitee 点击。静态导出版本不连接服务端，因此不会记录这些数据。

这个信息是可以直接带进面试的。你知道对方在你的"量化交易系统桥接"上停了四分钟、完全没翻 Android 那段，开场就能顺着讲。**这是单向投递给不了你的信息优势。**

## 更深一层的痛点：信任建立不起来

简历是一次**有损压缩**。十年经验压成一页 A4，压掉的全是证据：你写"精通 Android Framework"，HR 无法验证；他一天看两百份简历，每场面试三十分钟，最后只能靠学历、公司名气、话术流畅度这些**代理指标**下判断。

于是双方都难受：你被低估，他被将就。真正决定录用的从来不是"他简历写了什么"，而是"**我有没有足够证据相信他做得出来**"。

所以 OfferFolio 对内的定位不是"更好看的作品集"，而是**一条可下钻的证据链**：

```
第一层  结论     一句话 + 一个数字        → 让 HR 10 秒判断值不值得往下看
第二层  说明     做了什么、怎么做的、难在哪 → 让技术面试官判断深度
第三层  证据     代码 / 在线 demo / 原始截图 / 提交记录 / 可查编号 / 第三方背书
                 → 让怀疑的人自己验证，不用等你在面试里解释
```

大多数作品集只做到第一层，少数做到第二层。**第三层是空的**——而那恰恰是信任的来源。

后续可信度能力规划：

| 手段 | 为什么有效 |
|---|---|
| 每个项目挂**可点击的原始证据**（仓库、commit、发布记录、线上地址） | 把"我说"变成"你可以查" |
| 经历带**时间戳与量化口径**（不是"优化性能"，而是"延迟从 8ms 降到 1.2ms，压测脚本在此"） | 可复核的数字才有说服力 |
| 开源板块直连 GitHub，**提交热力图与贡献记录自动同步** | 第三方数据，改不了 |
| 敢写**失败复盘与踩坑记录** | 只报喜会触发怀疑，主动暴露缺陷反而增信 |
| 推荐语带**推荐人可点开的身份链接** | 匿名好评等于没有好评 |
| 站点内容与 PDF 简历**严格一致**（同一份数据源导出） | HR 一定会交叉比对，对不上就全盘崩塌 |

而这一层和访客雷达其实是**同一个闭环的两端**：雷达告诉你对方在哪块信息前停住了、哪块直接跳过，你就知道该补哪份证据给他。信任很少在一次面试里建立完成，它是几轮"对方存疑 → 你精准补证"累积出来的。OfferFolio 要做的，就是把这件事变成可执行动作，而不是靠临场猜。

## 核心能力：访客雷达

**服务端版记录访问，专属链接负责归因。** 服务端版中，无论访客直接打开主页，还是通过专属链接（`/r/{专属令牌}`）进入，后台都会创建访问记录。使用专属链接时，记录会额外关联到对应投递及其备注；直接打开则标记为普通访问。静态导出版本不带访问统计脚本，也不连接后台。不要根据 IP 推测访客姓名或身份。

### 当前第一版

- 所有公开主页访问的时间、请求来源 IP、入口类型，以及专属链接的投递备注
- 来源页面和来源分类汇总、终端浏览器与系统、浏览器语言，以及可选 UTM 来源参数
- 首次进入的展示模块，以及“联系我”、简历下载、GitHub 和 Gitee 的点击次数
- **模块阅读情况**：导航点击记录，以及页面处于前台且模块可见时累计的模块停留秒数
- 页面处于前台的累计停留时长
- 根据终端标记可能的机器人或邮件/社交链接预览访问；保留记录但不自动过滤
- 可设置保留 30、90、180、365 天，或关闭自动清理；启用期限会立即清理超期记录，并在后续访问时定期清理

每次进入公开主页都会生成一条访问记录；访问来源为专属链接时会沿用该条链接记录，不会因为重定向再重复计数。模块点击目前统计展示页导航点击；模块停留只计算前台页面中达到可见比例的模块。

### 后续规划

- 回访次数与间隔、滚动到 25% / 50% / 75% / 100% 的阅读深度
- 设备型号的细分识别、时区等更多访问上下文
- HR 打开后的实时提醒
- 抗误报清洗：识别 JS 执行的真实访问、过滤短暂命中、邮件安全网关与链接扫描器预抓取、爬虫及云厂商 IP 段

访问雷达对普通访问和专属链接访问一视同仁地记录；专属令牌只用于区分投递来源。IP 用于查看网络来源，不用于推测访客姓名或身份。

## 部署：本地优先，一台机器即可

OfferFolio 面向个人本地部署：公开作品集和管理后台由同一个 Next.js 服务提供，SQLite 数据库存放在本机或 Docker 数据卷中。Docker 部署使用单个轻量应用镜像。

- 本地开发无需独立数据库服务，内容写入项目目录下的 SQLite 文件
- Docker Compose 只启动 **一个应用容器**；不额外启动数据库、缓存或追踪服务
- 默认只绑定 `127.0.0.1`，适合先在自己的电脑上编辑和预览
- 后台支持一键导出静态页面 ZIP，可用于 GitHub Pages 等免费静态托管；静态版不需要数据库或常驻服务器，也不会记录访客数据

## 和同类方案比

| | 后台编辑 | 访客记录 | 可验证证据链 | 静态导出 | 数据归属 |
|---|---|---|---|---|---|
| developerFolio 等模板 | ❌ 改配置文件 | ❌ | ❌ 自己排版 | ✅ | 你的代码 |
| 招聘平台在线简历 | ✅ | ❌ 平台不给你看 | ❌ | ❌ | **平台** |
| DocSend 类文档分析 | 部分 | ✅ 但面向文档 | ❌ | ❌ | 你的账号（SaaS） |
| **OfferFolio（当前版本）** | ✅ | ✅ 服务端版可见；静态版不记录 | ✅ 内建三层下钻 | ✅ 后台一键 ZIP 导出 | **服务端数据在自己机器；静态托管副本由你选择平台** |

服务端版不接入第三方分析 SDK，也不做跨站追踪。选择静态托管时，发布包内的公开内容和媒体会由所选平台托管；静态版没有访客统计。

## 快速开始

### Docker 一键启动

```bash
git clone https://github.com/mynameyi/offerfolio.git
cd offerfolio
cp .env.example .env
```

编辑 `.env`，把 `ADMIN_PASSWORD` 改成长密码后启动：

```bash
docker compose up --build -d
```

- 公开作品集与管理后台共用 `http://localhost:5188`
- 后台入口：`http://localhost:5188/admin`
- SQLite 数据保存在 Docker 本地数据卷 `offerfolio-data`
- 停止服务：`docker compose down`；该命令会保留数据卷
- 备份数据库：`docker compose cp offerfolio:/app/data/offerfolio.sqlite ./offerfolio-backup.sqlite`

镜像只运行一个应用容器，不依赖数据库镜像。Compose 默认将端口绑定到本机回环地址，外网访问需自行配置 HTTPS 反向代理，并在 `.env` 中设置 `COOKIE_SECURE=true`。

### 从本地增量同步档案和媒体到远端

Windows 上可使用 `scripts/sync-remote-data.ps1`。它通过 SSH 比较本地和远端 `data/uploads/` 的 SHA-256，只压缩并上传新增或变化的媒体；数据库包只包含档案、投递话术和投递链接，远端按记录比较后更新。访客记录、访客统计设置和远端 `.env` 不会被同步或覆盖。远端已有但本地没有的媒体文件会保留；已从本地移除的投递链接会在远端停用，既有访客记录仍保留。

先部署包含 `scripts/import-deploy-data.mjs` 的新应用镜像并确认服务已启动，再运行：

```powershell
.\scripts\sync-remote-data.ps1 `
  -SshTarget "部署用户@服务器地址或SSH别名" `
  -RemoteDirectory "/opt/offerfolio" `
  -IdentityFile "C:/Users/用户名/路径/KO.pem" `
  -Preview
```

预览结果确认后，移除 `-Preview` 执行同步。首次会上传远端缺少的媒体；后续只传新增或内容有变化的文件。档案数据包体积很小，每次都会传输，但远端仅写入发生变化的记录。该脚本同步的是档案数据和上传媒体；如果部署流程使用 Docker 镜像 TAR 文件，镜像本身的传输仍由部署流程决定。

### 一键导出静态页面（GitHub Pages 等）

1. 登录 `/admin`，先保存最新的档案内容。
2. 点击右上角“导出静态页面”，浏览器会下载 `offerfolio-static.zip`。
3. 解压后，将 `index.html`、`robots.txt` 和 `assets/` 目录保持原有结构，一起上传到静态托管服务的网站根目录。
4. GitHub Pages：在目标仓库打开 **Settings → Pages**，选择发布分支与目录；把解压后的文件提交到该目录。仓库型 Pages（`用户名.github.io/仓库名/`）也可直接使用包内相对资源路径。

导出内容取自**最后一次保存**的档案，并包含页面引用的头像、图片、视频和必要样式。更新资料后，重新保存、导出并替换托管文件即可。静态版保留页面导航、深浅色切换、图片放大和项目媒体弹窗，但没有管理后台、SQLite、访客雷达或投递链接归因；数据也不会再同步回当前服务器。导出包中的档案和媒体对托管站点访客公开，发布前请检查隐私与授权。搜索引擎限制按导出时的后台开关写入包内 `robots.txt` 和页面元数据；如果求职展示结束，请从静态托管平台删除发布文件。

打开 `http://localhost:3000` 查看公开页面，`http://localhost:3000/admin` 编辑档案。数据库默认存放在 `./data/offerfolio.sqlite`。

## 关于隐私与合规

OfferFolio 面向求职投递阶段使用：网站通常只需在投递和面试期间短期公开，结束后可以停止托管，避免为不再使用的个人站点持续付费。默认开启的“减少搜索引擎留痕”开关会同时生成 `robots.txt` 全站抓取限制和页面 robots 元数据（`noindex`、`nofollow`、`noarchive`、`nocache`）；关闭后恢复允许抓取并移除这些页面指令。

这些指令是面向合规爬虫的请求，不会阻止普通访客访问，也不等于密码保护。被 `robots.txt` 禁止抓取的爬虫可能无法读取页面元数据；已被发现或收录的 URL 也可能继续出现在搜索结果中。不同搜索引擎对快照指令的支持不同，Google Search 已不再用 `noarchive` 控制缓存链接。规则遵循 [Robots Exclusion Protocol（RFC 9309）](https://www.rfc-editor.org/rfc/rfc9309.html)；Google 对 [robots 元标签](https://developers.google.com/search/docs/crawling-indexing/robots-meta-tag) 的说明也列出了当前支持范围。若需要保证内容不可访问，应关闭站点或加上访问认证；若需清除已有搜索结果，应通过对应搜索引擎的站长工具处理。

服务端版本的访问统计需要对访客保持透明。当前第一版的策略是：

- 使用带后台的服务端版本时，公开主页访问会记录访问时间、来源 IP、来源页面、终端信息、模块点击与停留时长；页脚会向访客说明
- 静态导出版本不加载访问统计脚本、不发送访问记录；静态托管平台仍可能按其自身规则保存服务器日志
- 当前会保存请求 IP 转发头中的完整地址；反向代理部署时需正确覆盖相关请求头。访问记录默认不自动清理，可在后台选择保留期限；启用后会删除超过所选期限的记录
- 不做跨站追踪，不加载任何第三方分析脚本
- 服务端版数据保存在自己的服务器上；静态版的发布文件由所选静态托管平台提供

后续可考虑 IP 前缀化或哈希存储选项。

一句话原则：**用它来判断"该往哪个方向准备面试"，而不是用它去骚扰任何人。**
